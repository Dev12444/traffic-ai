Traffic & emission reduction system
Mavericks Effect AI Challenge — full project spec and build plan
Team of 2  |  Submission deadline: July 30, 2026  |  Build window: 12 days (July 18–30)
1. Problem statement
Urban intersections run on fixed-timing traffic signals that don't adapt to real conditions. This causes avoidable congestion, wasted fuel, and higher emissions. We're building a system that watches traffic through CCTV, predicts congestion before it happens, and recommends adaptive signal timing plus alternate routes — with a couple of playful, genuinely useful civic features layered on top.
2. MVP scope — what "done" looks like
A working web app where:
	•	A simulated/recorded traffic video feed gets processed to count vehicles per lane, per intersection, over time
	•	That data feeds a prediction model forecasting congestion 15–20 minutes ahead
	•	A rule-based optimizer computes recommended signal green-time splits based on current + predicted load
	•	A live dashboard (map-based) shows current congestion, predicted congestion, and suggested alternate routes
	•	Summary stats show estimated time/emission savings vs. fixed-timing baseline
	•	A "forgot your helmet?" toggle that reroutes around manually-marked police checkpoints

MVP is NOT: real government CCTV integration, real-time production deployment, hardware signal control, or automated police detection. It's a convincing, technically real simulation of the full pipeline — which is exactly what hackathon judges want to see.
3. Tech stack
Backend / AI
	•	Python (FastAPI) — inference service for vehicle detection + prediction
	•	Node.js (Express) — main API server, orchestration, business logic
	•	YOLOv8 (Ultralytics, pre-trained on COCO, filtered to vehicle classes) — vehicle detection
	•	PyTorch or TensorFlow — LSTM/GRU congestion prediction model
	•	PostgreSQL + PostGIS (via Supabase) — spatial data, time-series storage
	•	pgRouting — shortest-path and constrained routing queries
	•	Redis (optional, if time permits) — caching live state for fast reads
Frontend
	•	React + Vite
	•	Mapbox GL JS (react-map-gl) — live heatmap, routes, markers
	•	Recharts — stats/trend charts
	•	Tailwind CSS
Data sources
	•	Traffic video: public dashcam/CCTV footage from YouTube (via yt-dlp) or a Kaggle traffic video dataset
	•	Historical traffic patterns: Kaggle "Traffic Prediction Dataset" or METR-LA / PEMS-BAY (standard traffic ML benchmarks)
	•	Road network: OpenStreetMap export (via Overpass API) for a real Ahmedabad-area grid, or a hand-built synthetic grid if OSM data is messy
	•	Weather: OpenWeatherMap free API
Infra / deployment
	•	Backend: Render (free tier) — both Node and Python services
	•	Frontend: Vercel
	•	DB: Supabase (managed Postgres + PostGIS)
	•	Version control: GitHub — shared repo, branch-per-feature
Prerequisites to install before Day 1

4. System architecture — ownership split
Person A owns the AI/ML pipeline (video ingestion → vehicle detection → prediction model). Person B owns backend API, database, and frontend dashboard. The seam between you is a simple, well-defined API contract, so you can work almost fully in parallel with minimal blocking.
Either of you can take either role — pick based on who's more excited about computer vision vs. who's more excited about geospatial/dashboard work.
Person A: AI/ML pipeline
	•	Video ingestion — yt-dlp + OpenCV framing
	•	Vehicle detection — YOLOv8 counts per lane
	•	Prediction model — LSTM forecasts congestion
	•	FastAPI inference service exposing /predict
Person B: backend + frontend
	•	Node.js API + Supabase — schema, storage, endpoints
	•	Signal + route optimizer — PostGIS rule engine
	•	React + Mapbox dashboard — live heatmap, routes, stats
	•	Deployment — Render + Vercel
Predictions and counts flow from Person A's model into Person B's database via a shared API contract — agree on this contract on Day 1 before either of you writes real logic.

	•	Build PostGIS-based alternate routing: given a congested intersection, compute 1–2 alternate paths using pgRouting or simple Dijkstra over the road graph

6. Database schema reference
create table intersections (
  id uuid primary key default gen_random_uuid(),
  name text,
  geom geography(Point, 4326)
);

create table vehicle_counts (
  id uuid primary key default gen_random_uuid(),
  intersection_id uuid references intersections(id),
  timestamp timestamptz,
  lane_counts jsonb  -- {N: 8, S: 5, E: 3, W: 6}
);

create table predictions (
  id uuid primary key default gen_random_uuid(),
  intersection_id uuid references intersections(id),
  predicted_for timestamptz,
  predicted_count integer,
  confidence float
);

create table signal_timings (
  id uuid primary key default gen_random_uuid(),
  intersection_id uuid references intersections(id),
  timestamp timestamptz,
  ns_green_secs integer,
  ew_green_secs integer
);

create table checkpoints (
  id uuid primary key default gen_random_uuid(),
  name text,
  geom geography(Point, 4326),
  active_from time,
  active_to time,
  notes text
);

8. Feature spec: "Forgot your helmet?" toggle
Since automated police detection isn't reliable for Indian traffic-vest variations, checkpoints are manually seeded data for the MVP — this is intentional and should be described as such, not hidden.
User flow
	•	User requests a route from A to B (normal flow)
	•	Before showing the route, the UI shows a toggle: "Forgot your helmet?"
	•	If off (default) → show the normal fastest/optimized route (may pass checkpoints)
	•	If on → route optimizer adds a constraint: avoid any path segment within ~150m of an active checkpoint → recompute route via PostGIS, show the alternate path with a note like "This route adds ~3 minutes but skips 2 checkpoints"
Framing for judges — say this in the pitch
"We added a lighthearted feature: if you forgot your helmet, the app can suggest a fully legal alternate route and reminds you why — no rule-breaking, just smarter path choice, the same way a nudge app might warn you about speed cameras. It's also a great showcase of our routing engine's flexibility — the same PostGIS pathfinding that optimizes for congestion can optimize for any constraint you feed it."
Note: control this narrative proactively. If a judge asks whether this helps people evade checkpoints, the answer is: the routing itself is 100% legal (public roads, no rule broken) — this is a reminder + route choice tool, not an evasion tool.
Other smart nudge features (stretch, same pipeline)
	•	"Signal's about to flip red in 8 seconds" — congestion-prediction-based nudge, no extra ML
	•	"This lane's had zero violations today" — lighthearted best-behaved-intersection leaderboard
	•	"Rush hour roast" — auto-generated one-liner for whichever intersection has worst congestion right now
9. Full feature list
Core (must-have for MVP)
	•	Vehicle detection from video feed (YOLOv8), counts per lane per intersection
	•	Time-series storage of traffic counts (PostGIS + Supabase)
	•	Congestion prediction 15–20 minutes ahead (LSTM)
	•	Rule-based adaptive signal timing recommendation
	•	Alternate route suggestion avoiding predicted congestion (PostGIS/pgRouting)
	•	Live map dashboard: current congestion heatmap
	•	Predicted congestion overlay on map
	•	Route visualization with ETA
	•	Summary stats: estimated time saved, emissions reduced, % rerouted
	•	"Forgot your helmet?" checkpoint-avoiding reroute toggle
Stretch (if ahead of schedule)
	•	Multi-intersection network view (8–12 intersections instead of 2–3)
	•	Historical trend charts (Recharts) — congestion over the day/week
	•	Weather-aware prediction (rain/heat affecting traffic patterns)
	•	Simple auth for a "city admin" view vs. public view
	•	Redis caching for faster live reads
	•	Confidence intervals shown on predictions (not just point estimates)
	•	Mobile-responsive dashboard
	•	"Rush hour roast" and best-behaved-intersection leaderboard nudges
Explicitly out of scope
	•	Real hardware signal control
	•	Real government CCTV API integration
	•	Production-scale video processing (multiple simultaneous live streams)
	•	Automated police/helmet detection (manual checkpoint data instead)
